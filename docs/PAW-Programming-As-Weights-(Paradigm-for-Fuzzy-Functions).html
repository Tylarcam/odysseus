Paper Summary: Program-as-Weights (PAW)

Researchers from the University of Waterloo, Cornell, and Harvard introduced PAW, a system that treats a large language model (LLM) as a compiler rather than a chatbot. Instead of sending a prompt to a massive model (like Qwen3-32B) for every request, you provide the task specification to a 4B compiler model once. The compiler emits a 23MB adapter (the "Program") that can be plugged into a 0.6B local interpreter model.

This system allows a tiny local model to match the accuracy of a 32B model while running at 30 tokens/second on consumer hardware (like an M3 MacBook) with 1/50th the memory footprint, entirely offline.

Similar Ideas and Related Research

The following table compares the PAW paradigm with existing technologies that share similar goals of local efficiency and task-specific optimization.

Paper / Project Core Idea Similarity to PAW Key Difference
LoRAX (LoRA Exchange) Serving thousands of task-specific adapters on a single base model. Uses adapters to define specific task behaviors. Focused on serving/infrastructure rather than a "compilation" paradigm.
DSPy (Stanford) Compiling declarative prompts into optimized instructions or few-shot examples. Uses a "compiler" metaphor to improve small model performance. Optimized prompts/weights via training, but doesn't usually generate a standalone "weight file" program.
Skeleton-of-Thought Parallelizing LLM generation by splitting tasks into sub-tasks. Aims for local speed/efficiency. Optimization is at the inference level (parallelism) rather than the weight/model level.
TinyLlama / Qwen-0.5B Training extremely small base models from scratch. Provides the "interpreter" layer for local execution. These are general-purpose base models, not task-specific "programs."
BitNet b1.58 1-bit LLMs where weights are -1, 0, or 1. Drastic reduction in memory and increase in local speed. Hardware-level optimization rather than a programming paradigm for "fuzzy functions."

Implementation Guide: Using PAW with Odysseus

Odysseus (the self-hosted AI workspace popularized by PewDiePie) can be used to implement this "Compile Once, Run Anywhere" workflow by utilizing its support for Ollama and Custom OpenAI-compatible endpoints.

Step Action Technical Details
1. Compilation Define your task in natural language. Use the PAW 4B Compiler model (e.g., via the programasweights/paw-4b weights on Hugging Face) to generate a .bin or .safetensors adapter for your task.
2. Adapter Export Save the 23MB adapter file. Each "function" (e.g., "Summarize emails," "Extract dates") becomes a unique weight file stored locally.
3. Setup Backend Run a local inference server. Use vLLM or LoRAX to host the Qwen3-0.6B base model. These backends allow you to dynamically load your PAW adapters via an API.
4. Local Tunnel Expose the model to Odysseus. If using Docker for Odysseus, ensure the server is listening on 0.0.0.0 and allow CORS, or use the [http://host.docker.internal:port](http://host.docker.internal:port`) endpoint.
5. Add to Odysseus Register the "Fuzzy Function." In Odysseus Settings > Models > Local, add a new model. Set the URL to your local server (e.g., [http://127.0.0.1:11434/v1](http://127.0.0.1:11434/v1`)) and use the adapter name as the model ID.
6. Execution Run the task offline. Select the specific "Function-Adapter" in the Odysseus chat interface. The 0.6B interpreter will execute the task locally with 32B-level accuracy.
